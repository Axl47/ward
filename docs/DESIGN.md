# Ward design

Status: approved 2026-11-19 and built. Where the build departed from the draft, this file now describes what was built.

Names used here: gaia-arch is the Arch Linux workstation Ward was built on, and omarchy-config the repo recording its setup; Annex is the T3 Code fork that carries Ward's hook; [Puck](https://github.com/Axl47/puck) drives a desktop for agents; Caliban and Miranda are the author's own private tools for capturing a desktop's audio and recording a screen and terminal timeline.

## Problem

T3 gives each thread its own git worktree, so files don't collide. Everything else on gaia-arch is shared: the loopback port space (two Vite servers both want 5173), Docker (shared daemon, published ports, fixed `container_name`s), `/tmp`-based caches such as Metro's, and the adb server. Ward gives each worktree a private copy of those, created on demand and removed when the worktree goes away.

The threat model is accidental collision between trusted agents, not containment of a hostile one. The red team of 2026-11-20 showed how far a ward command acting deliberately could reach; Ward now closes the paths that cost little to close (below, "What a ward sees of the host's files"), and Risks lists those still open. That rules out microVMs as the default: they would buy security we don't need and cost file-system speed (virtiofs over `node_modules`) and nested KVM for emulators.

## What T3 offers today (Annex, verified by reading the code)

- Worktrees are created in `ThreadLaunchService` → `GitVcsDriverCore.createWorktree`, at `<worktrees folder>/<repo>/<branch-prefix>-<16 hex>`, where the folder is `~/.t3/worktrees` or T3's `worktreesDirectory` setting. The thread ↔ worktree link lives only in `statev2.sqlite` (`orchestration_v2_projection_threads.payload_json.$.worktreePath`).
- Removal happens on many paths: launch failure, UI remove, handoff failure, and an hourly storage-cleanup job. Thread archive and delete never remove the worktree. "Settle" is a flag on the thread, not a removal.
- `t3.json` scripts can run on worktree create and on settle, but only the first matching script runs, they are per project, they get no thread id, and nothing runs on removal.
- Claude and Codex get `T3CODE_THREAD_ID`; terminals have every `T3CODE_*` variable stripped.
- Annex already has a `PortScanner.PortDiscovery` service that watches agent-started ports.

So the hook Ward needs, wrapping every process a thread starts, doesn't exist. It belongs in Annex as one small hook; everything else, including reacting to worktree removal, lives in Ward.

## The isolation unit: one ward per worktree

A ward is an unprivileged Linux **user + network namespace** pair (no root, no setuid). Keyed by worktree, because two threads on one worktree already share files.

```
host (init namespaces)                         ward "indexio/t3-d7059d66…"
┌───────────────────────────────┐              ┌──────────────────────────────────┐
│ T3 server ── spawns ──────────┼─ ward exec ─▶│ agent shell commands, dev server │
│                               │  (nsenter +  │ :5173, Metro :8081               │
│ wardd (user service)          │   cgroup)    │ podman API ─▶ postgres :5432     │
│  · host port block 20100-199 ◀┼── fd broker ─┤ its own 127.0.0.1, own ports     │
│  · reconciler                 │              │ pasta: internet + host :3773 (T3)│
│  · each ward's emulator       │              │ its own adb server, one device   │
│ adb server :5037, emulators   │              └──────────────────────────────────┘
└───────────────────────────────┘
```

- **Namespaces.** `unshare --user --net` with a custom ID map: your uid maps to itself (1000), so files in the worktree stay yours and nothing runs as root (Postgres `initdb` and Chromium's sandbox both refuse root); uid 0 and the rest map to your subuid range for the container engine. Proven on this machine with a single-uid map: a server bound inside is invisible to the host, processes that join see it, and files they create are owned by you. The full subuid map worked too. Because it is a user namespace, `sudo` and other setuid programs can't work inside; a `sudo` shim says so. Each ward also has a mount namespace, in which ward commands see the host's files with a few locked down (next bullet but one), and a PID namespace, so a ward sees and signals only its own processes: before, every ward shared the host's process table, and since your uid is the same in every ward, `kill` across wards passed. `catatonit` is its init (pid 1 ignores signals it has no handler for, and must reap orphans), and when the ward stops the kernel kills what is left. Joining the PID namespace makes `nsenter` fork and stay outside as the command's pid without passing signals on, so `ward exec` gives the command a parent-death signal (SIGTERM): a caller that kills the pid it started still stops the command. Pids inside are the ward's own: `ward-init` translates the namespace holder's to the host's for the `pid` file, and a ward desktop's `pid` is looked up through the ward's `/proc` (`/proc/<holder>/root/proc`) from outside it.
- **cgroup.** Each ward is a systemd user unit, `ward@<id>.service`, in `app-t3code-agents-wards.slice` so it shares the memory limit T3 puts on agents. `ward exec` moves the command into that cgroup before entering the namespaces, so stopping the unit (`KillMode=control-group`) kills every process the agent started, including daemonized dev servers and container processes, and gives per-ward CPU accounting. Containers run with Podman's cgroups disabled (crun, not runc), so they share the ward's cgroup.
- **Internet.** `pasta` (from `passt`), started as root inside the user namespace, attaches to the ward's netns for outbound traffic and forwards a short allow-list of host loopback services into it: DNS (the host's stub resolver), `WARD_HOST_PORTS`, default T3's server on 3773, and the project's own list, stored in its `ward enable` marker (`ward enable <repo> --host-ports 39003`). `wardd` writes each ward's combined list to its runtime folder when it starts, so a change applies when the project's wards next start.
- **Who may call `wardd`.** Its control socket is `$XDG_RUNTIME_DIR/ward/wardd.sock`, and that folder is shared with every ward (see Risks), so the path admits ward processes too. `wardd` therefore asks the kernel who connected (`SO_PEERCRED`, through `node:ffi`, since Node has no API for it) and compares the caller's network namespace with its own and with each ward's: a ward can neither forge nor leave its namespace. The host may call anything. A caller in a ward may only map its own ports, start its own desktop, start and stop its own device, and list its own ward and device (`ward port`, `ward desktop`, `ward device`, `ward ports`, `ward devices`; and, in a ward started before wards had their own adb server, start the host's, for the `adb` shim); a request naming another ward, or any other route (`up`, `stop`, `rm`, `gc`, a thread's desktop), is refused with 403, as is a caller of another uid or in no ward's namespace. This holds only while ward processes stay in their namespace: anything that lets one start a process on the host (see Risks) gets that process the host's rights here too.
- **What a ward sees of the host's files.** The same file system as the host, with these changes, made in the ward's mount namespace when it starts (`libexec/ward-init-root`) and joined by `ward exec` (`nsenter -m`):
  - *No systemd user manager, and a filtered session bus.* `$XDG_RUNTIME_DIR/systemd` is an empty folder, and `$XDG_RUNTIME_DIR/bus` is a proxy (`xdg-dbus-proxy`, started by `libexec/ward-init` in the ward's cgroup) through which only the keyring (`org.freedesktop.secrets`) can be reached, which `gh` and `git` need. Without this, `systemd-run --user` from a ward started a process in the host's namespaces, outside the ward's cgroup, that `ward stop` didn't kill, and every service on your bus (portals, the systemd manager) was the ward's to call. Without `xdg-dbus-proxy` the ward has no session bus.
  - *Ward's own files are read-only.* The host trusts them: it runs the checkout, sources each ward's `env`, reads the enable markers whose `--host-ports` set what pasta forwards, and wardd trusts the registry and the thread notes. So `$XDG_STATE_HOME/ward`, `$XDG_RUNTIME_DIR/ward` and the checkout are read-only, except the ward's own state folder (its `TMPDIR` and Podman store), its desktop's folder and its Podman socket's folder. `ward-init`, on the host side, writes the `pid` and `ready` files that `ward-init-root` reports, and a desktop's `env`, which is written inside the ward, is read as data rather than sourced.
  - *Other wards' data is not there.* Of Ward's state folder a ward sees only its own folder and the shared image store, read-only; other wards' folders (their container stores and volumes), the trash and thread desktops' data are absent. This is what keeps container stores apart: every ward maps its root to the same host uid (one subuid range), so file ownership doesn't.
  - *Credentials are hidden.* Ward's config folder shows only `enabled/` (read-only), so its T3 token is gone, also one written after the ward started. Each T3 home's `userdata` (`~/.t3*/userdata`: T3's keys under `secrets`, and its databases with every project's threads) shows only `attachments`.
  - *Miranda's store is hidden.* `~/.local/share/miranda` (or the `MIRANDA_HOME` wardd runs with) holds the user's screen and terminal timeline, Glosses, every agent's recorded commands and the control file that turns recording on, and before this a ward command could read and write all of it. A ward sees it as an empty read-only folder with only `shell`, where Miranda's bash hook leaves the commands typed in a ward's terminal (it can still read those for the second before Miranda takes them, and add lines). Miranda's MCP server runs on the host, so agents keep its tools; its CLI inside a ward has no store. A store created after a ward started is visible in that ward until it restarts. Like the paths above, the folders over it (`~/.local/share`, `~/.local`) become mount points in the ward.
  - *Your Gradle home and Kotlin daemon folder are the ward's own.* `~/.gradle` (or the `GRADLE_USER_HOME` wardd runs with, at its real path) is covered by `gradle` in the ward's state folder, and `~/.local/share/kotlin/daemon` (under the `XDG_DATA_HOME` wardd runs with, if set) by `kotlin-daemon`, at the same paths, so paths under them are the same in every ward and on the host, tools that ignore `GRADLE_USER_HOME` are covered, and yours are out of the ward's reach. When wardd has `GRADLE_USER_HOME`, a ward's env has it too, and only that folder is covered: `~/.gradle` is then shared as before. Over the home, `gradle.properties` and `init.d` are read-only mounts of what wardd writes in the ward's runtime folder. The build cache store (`~/.local/state/ward/build-cache`) is not in a ward's view of Ward's state folder. Caches says why. A ward started before this keeps the shared home until it is stopped and started.
  - *Locked.* The changes are made in the user namespace `unshare` creates, and the ward runs in a second user namespace nested in it, with the same id map. Mounts inherited from a namespace owned by a more privileged user namespace are locked, so not even the ward's root, which any ward command can drive through Podman's socket, can unmount or remount them. A folder above one of these paths that you could rename (one whose parent is yours) is made a mount point too, so a ward can't move it aside and put a forged copy where the host looks. A ward command can't read `/proc/<pid>/root` of a host process either (measured), so nothing reaches the files beneath.
  - *Back to its folder by path.* Joining a mount namespace moves a process to its root, so `ward exec` changes back to the caller's folder by path inside the ward; `nsenter --wd` would carry the folder in from outside, and relative paths from it reach what the namespace hides (measured).
- **Start errors.** journald drops what is written from inside the ward's user namespace, so the init scripts' stderr goes to `init.log` in the ward's runtime folder; `wardd` puts its tail into the error when a ward fails to start, and logs its warnings (such as a TCP sysctl it couldn't set) when it starts.
- **Containers.** Each ward runs its own Podman API service as root-inside-the-ward, in a private mount namespace with its own `/run` and `/var/lib/containers`. Agents use the normal `docker` / `docker compose` CLI via `DOCKER_HOST`. Published ports land in the ward's own loopback, so `docker run -p 5432:5432 postgres` just works in every ward at once. Each ward pulls into its own store by default; `ward images pull IMAGE` puts an image in a shared read-only store (Podman `additionalimagestores`) that every ward reads, so it's downloaded once. The store is read-only in every ward's mount namespace, and no ward sees another's store (below), which matters because every ward's root is the same host uid. This also means you never need the root-equivalent `docker` group. Podman's healthchecks normally run from systemd timers, which a ward lacks, so `wardd` runs them at each container's configured interval (compose `depends_on: service_healthy` works). Builds use Docker's classic builder (`DOCKER_BUILDKIT=0`), since BuildKit's builder container needs a cgroup of its own. Container DNS (aardvark-dns) listens on port 1153, because 53 in the ward is pasta's DNS forward. Podman sees a private `/var/cache`, where root's Podman records short-name aliases, so `postgres:17` resolves as on the host. `ward stop` stops containers with a 10-second grace period (Docker's default, so a database can shut down cleanly) before stopping the unit, so one that ignores SIGTERM doesn't hold the stop for the unit's 15-second timeout and leave it failed. `wardd` follows each ward's Podman event stream and lists containers only on a change (and once per connect; a failed list is retried, backing off to 30 s), so an idle ward costs Podman nothing.
- **Caches.** Lock-safe content-addressed caches stay shared (pnpm store, Cargo registry). Gradle's are per ward, with a build cache shared through wardd. One shared Gradle home cost every build in a second ward a wait of about 9 s on its journal lock and stopped the other ward's daemon: a client that can't reach a daemon over the ward's loopback removes it from the shared registry, and the daemon exits. With a registry per ward over the shared home, the second ward's build failed after 60 s on that lock instead, since an idle daemon only lets go of its locks when pinged over loopback, which can't cross wards. Kotlin daemons keep their run files outside the Gradle home, in a folder wards would otherwise share with each other and the host. So each ward gets its own Gradle home and Kotlin daemon folder, mounted over yours (see above; `src/gradle.ts`).
  - *The home.* wardd makes it when the ward starts without one, and touches the ward's state folder only then, while the ward's unit is stopped, since the ward owns that folder: anything at `gradle` (or `kotlin-daemon`) that isn't a real folder, such as a link the ward left, is removed, never followed, and so is the clone's temporary folder. If the worktree has a Gradle build (`gradlew`, `settings.gradle` or `settings.gradle.kts` at its root or one folder down, as React Native keeps it in `android/`), the home is a reflink copy (`cp --reflink=always`) of your `caches/modules-2`, `caches/jars-*`, `caches/transforms-*`, `caches/<version>/` and `wrapper/`, with their lock files (a cache copied mid-write then reads as not cleanly closed) and without `gc.properties`. That took about 1.4 s for a 2 GB home, and each ward's home was 1.94 GiB in total but 4.7 MiB of its own on btrfs. Eight wards created while host builds kept rewriting the source home's dependency caches all built `--offline` cleanly. Other wards, and every ward off a reflink file system (wardd logs it), start with an empty home. So a ward's dependencies are a snapshot from when it was created, and a dependency added later is downloaded once in each ward.
  - *Your settings.* On every `up`, wardd writes `gradle/gradle.properties` in the ward's runtime folder as yours plus `org.gradle.daemon.idletimeout=600000` (10 minutes instead of 3 hours) unless yours sets it, and `gradle/init.d` as your regular `*.gradle` and `*.gradle.kts` files plus `ward-build-cache.gradle`, and ward-init-root mounts both read-only over the home's when the ward starts. wardd rewrites them in place, so a running ward sees yours as they were at its last `ward up`. When the project configured no remote cache, that static script points the build's remote cache at `http://127.0.0.1:5071/cache/` with push on and turns the local one off; a project's own remote cache is left alone, and whether a build uses a cache stays the project's `org.gradle.caching`.
  - *The build cache.* Port 5071 is the broker's on each ward's loopback, and it hands what connects to wardd's cache server, so wardd knows which ward calls and no listener exists on the host; `ward port` refuses it and `ward ports` never lists it. Entries live in `~/.local/state/ward/build-cache/<repo>/<key>`, one folder per project, so a project's wards never read entries another project's wrote; deleting a project's folder clears its cache. Keys are 32 to 128 lowercase hex characters; an upload is written aside and renamed, so an entry appears whole or not at all; an empty upload gets 400 and one over 1 GiB 413 (counted as it arrives); a read marks the entry used. At start, hourly, and as soon as uploads since the last sweep pass a tenth of the cap, wardd deletes the least recently used entries until the store is under `WARD_BUILD_CACHE_MAX` (bytes, or with K, M or G; default 10G), keeping any used since it listed them, and uploads abandoned for an hour. With wardd down, Gradle turns the remote cache off for that build and carries on; `--offline` turns it off too, so offline builds in a ward have no build cache, and `--no-build-cache` skips it for one build.
  - *Measured* on an Android project (`:core-domain:test :app:compileDebugKotlin`, two wards): a cold build in ward A took 52 s (72 tasks executed); the same target in ward B, never built there, took 12.8 s, with 81 of 96 tasks from the cache and the other 15 tasks ones Gradle never caches. Cache keys were the same in both wards despite their different worktree and Android SDK paths. Builds alternating between the wards took 0.8–3.7 s with no lock waits and the same Gradle and Kotlin daemons before and after, and both wards building at once succeeded. An idle building ward holds about 4.5 GB (Gradle daemon 1.3 GB, Kotlin daemon 3.2 GB with the project's `-Xmx4096m`); all its daemons exited about 10 minutes after its last build (the Kotlin daemon exits when its Gradle daemon does). A second run on a loaded machine (load 11 to 37 on 12 cores) had the same task counts and daemons but took 62 s cold and 21 s from the cache; a quiet rerun hasn't been done.
  - *Limits.* Any ward of a project can write an entry the project's other wards use, and which wards are a project's is decided as for everything else in Ward. The host's own builds don't read this store. A project that listens on 5071 in a ward clashes with the cache. Each building ward runs its own daemons. Port 5071 can't be a forwarded host port (`--host-ports`), and a ward holds at most 64 connections to the cache. Your Gradle home is only as safe as before from a ward that can still write it: one started before this change, until it is stopped and started, or any ward when the home is reached through a symlink in a folder wards can write (wards can't replace a real folder, which is a mount point in each). Such a ward can change the settings wardd gives the others at their next `ward up`. If wardd can't prepare a ward's own home when it starts (logged), the ward starts on your shared one, as before this change. Init scripts that are symlinks are not copied.

  Per-ward: `TMPDIR` (covers Metro, Vite and most tools), the container store, and volumes. `/tmp` itself is the host's: a tool that writes a fixed `/tmp/...` path shares it with every ward and the host. A private `/tmp` would now cost nothing more (wards have a mount namespace that every command joins), but it would cut the handoff of files through `/tmp` between agent commands in the ward and everything on the host (the agent's own file tools, T3, screenshots, X11 sockets), so Ward doesn't make one.

## Ports

No allocation inside the ward: every ward can use any port, including hardcoded ones. Allocation only exists at the boundary, for things outside the ward that need to reach in (your browser, T3's preview browser, emulators).

- Each ward gets a slot N and a host block `20000 + 100·N … +99` (below the ephemeral range 32768+).
- `wardd` watches the ward's listening sockets (`/proc/<pid>/net/tcp*` is per-netns) and maps each new one to the next free port in the block, stable for the ward's life: ward `:5173` → host `127.0.0.1:20103`. Each ward's namespace gets a TCP hash table of its own (4096 buckets), so these once-a-second reads don't walk the host's table; the two limits the kernel derives from the table's size (`tcp_max_tw_buckets`, `tcp_max_syn_backlog`) are set back to the host's values, or a load test in a ward would overflow TIME_WAIT.
- Mechanism: `wardd` listens on the host port itself. For each incoming connection, a tiny broker process inside the ward (joined with `nsenter`, talking over Node IPC) dials the ward port and passes the connected socket back, without reading from it. The broker carries no traffic, but `wardd` copies every byte between the two connections in userspace (half-close included), which costs about 22 % of keep-alive throughput and 16 % on a large download against the ward's port reached from inside it ([PROFILE.md](PROFILE.md)). Decided: that cost is accepted, not a to-do. A later live test measured 2.14 GB/s through a mapped port against 2.20 GB/s direct for 1 GiB with `curl`, and 517 ms against 452 ms for 5000 new connections; a dev server never needs more. The listener keeps half-close (a client can send FIN and still read the reply, and so can a server), and when the ward stops or `wardd` exits its connections are reset rather than ended, so a client can't mistake a cut-off download for a complete one; a `wardd` restart drops connections in flight. The profile once saw a 64 MiB download through a mapped port hang; it was never reproduced: not in 200 runs of the same download through the broker and copy path in `test/forward.test.ts`'s harness, nor through live mapped ports since. Ruled out: the half-close handling (fixed, and pinned by tests) and loss in the broker (it never reads from the socket it hands over). Ports Podman publishes are DNAT rules rather than listening sockets, so `wardd` also follows the ward's Podman event stream and asks which ports its containers publish whenever one starts or stops.
- Mappings live in `~/.local/state/ward/registry.json`. When a ward port stops listening, its host listener closes (connections are refused, not reset) but keeps its number. When a ward's block of 100 is full, a mapping whose ward port stopped listening is released.
- Host ports bind 127.0.0.1 only, so other devices on the LAN or tailnet can't reach a ward's servers.

## How an agent finds its ports and services

Mostly it doesn't need to: inside the ward, services are at their usual `localhost` ports. The ward's env carries `WARD_ID`, `WARD_ROOT`, `DOCKER_HOST`/`CONTAINER_HOST` and a per-ward `TMPDIR`; adb finds one device, the ward's own, so nothing sets `ANDROID_SERIAL`. For the only thing that differs, host-visible URLs, `ward ports` prints the mapping and `ward port 5173` maps one on demand. Nothing is written into the worktree, so `git status` stays clean. A note in the global agent instructions says this, and that the preview browser needs the host URL, since it runs outside the ward.

An MCP tool isn't needed in v1. T3's port list shows each ward port at its host address, attributed to the worktree's thread.

## Devices

Goal, in the words of the request (2026-11-22): "Give each ward its own Android emulator: a 'private device' that works like Ward's private desktop. It's created on demand, only that ward can use it, it stops when idle or when the ward stops, and the next use gets a fresh one. Today every T3 thread shares three AVDs (`agent-1..3`, booted as emulator-5554/5556/5558), and threads stomp on each other: thread B opens or modifies the emulator thread A is using mid-test. The user wants agents to work on Android in parallel without that happening."

Two things let threads collide before this. T3's `device_open` never checked whether another thread held the device (Annex's to fix: it now leases the shared ones). And a ward reached the host's adb server whole: pasta forwarded port 5037, so any ward command could `adb -s emulator-5554 …` onto another agent's emulator or onto your phone, and Gradle's `installDebug`, which talks to the adb server itself and installs on every device it lists, did so without being asked. An earlier version of this section left leasing to T3 and gave Ward only the plumbing. That is superseded: Ward owns ward devices, T3 leases the shared ones.

```
ward "app/t3-d7059d66…"                      host
┌────────────────────────────────┐          ┌──────────────────────────────────────────┐
│ adb, Gradle, Expo, RN          │          │ wardd                                    │
│  └ :5037 (the broker's) ───────┼─────────▶│  starts the device if the request needs  │
│                                │          │  one, then connects the client to :5038  │
│ the ward's own adb server ◀────┼──────────┤                                          │
│  :5038, stock adb              │          │ ward-device-<id>.service                 │
│  └ :5585 (the broker's) ───────┼─ wardd ─▶│  emulator -avd ward-base-<key>           │
│    its only device:            │          │    -read-only -port 5584   :5584, :5585  │
│    emulator-5584               │          │           ▲                              │
└────────────────────────────────┘          │ host adb server :5037 ── emulator-5584   │
                                            │  T3: Device panel, agent-device          │
                                            └──────────────────────────────────────────┘
```

- **One base image, any number of read-only instances.** Ward keeps one AVD of its own, `ward-base-<key>`, with a saved boot snapshot, in its own AVD home (`~/.local/state/ward/device/avd`, hidden from wards and absent from `emulator -list-avds`). A ward's device is `emulator -avd ward-base-<key> -read-only`: the emulator then writes to temporary overlays instead of the AVD, so any number run at once from one image, each starts from the snapshot (measured: 4 s to a booted Android, three in parallel as fast as one), and stopping one leaves nothing behind. The emulator refuses a read-only instance while a writable one of the same AVD runs, which is why the base is never booted writable once it is built. Copies of an AVD were the alternative: 6 GB and a 27 to 68 s cold boot each, since NOCOW AVD files can't be reflinked and a copy taken while its emulator runs has no loadable snapshot.
- **On the host.** An emulator started inside a ward would bind its console and adb ports in the ward's network namespace, where the host's adb server and T3 can't see it. So `wardd` starts each one on the host, as a transient unit `ward-device-<id>.service` under the wards' slice (as thread desktops are, so devices count toward the agents' memory limit), with `TMPDIR` set to a folder of its own on disk, `~/.local/state/ward/device/run/<id>`. That folder matters twice: the overlays would otherwise go to `/tmp`, which is memory here; and the emulator finds its radio simulator (`netsimd`) through the temp folder, so each device gets one of its own, which stops with the unit, rather than sharing the one your other emulators use and taking it down with it. The unit stops with `KillMode=mixed`: the emulator gets the stop signal alone, and what is left (netsimd, the adb server it starts for itself) is killed once it exits. Signalled together, netsimd went first and the emulator aborted in its gRPC teardown with a core dump of about 1 GB, on every stop; and that adb server ignores SIGTERM, so a base build's unit sat out its 10 s stop timeout and failed after the image was already saved (measured 2026-11-22). The unit survives a `wardd` restart; `wardd` finds its devices again from the `device.json` each leaves in that folder. Its `OOMScoreAdjust` is raised: when memory runs out, a device, which is replaced by a fresh one anyway, goes before an agent's process.
- **The base image builds itself.** Its name carries a key: a hash of the emulator's and the system image's `source.properties`, the system image's `build.prop`, the template's `config.ini`, the GPU mode and the build recipe's version. A device start that finds no ready base for the current key builds one alongside any older one: writes the AVD (its `config.ini` copied from a template AVD of yours, by default the first by name in `~/.android/avd` when `wardd` first looks (usually its first reconcile), which it then keeps to (written down in `device/template`, so an AVD you make later changes nothing), or `WARD_DEVICE_TEMPLATE`; the template is only read, never booted), cold boots it writable with no window, waits until Android answers and a few seconds more, then stops it with SIGINT so the emulator saves `default_boot`. Measured: 40 s in all, so the first device ever, and the first after an emulator or system image update, takes about 45 s instead of 5. Devices running from the older base are not disturbed; an older base is deleted when no device runs from it. No adb server ever sees the base while it builds: it listens on a console port from 5690 up (outside the 5554 to 5585 range adb servers scan), is told with `ANDROID_ADB_SERVER_PORT` that the adb server is on a port of its own, so it never announces itself to the host's (the emulator starts an adb server there for a setup command of its own, with USB, mDNS and the emulator port scan off, which stops with the build), and `wardd` reads its boot from the emulator's log (`Boot completed in … ms`) instead of asking over adb. An install from the host in those seconds therefore can't land on the image every ward's device is made from. A device that boots without loading the snapshot (the emulator's log says so) gets a cold boot's 120 s instead of 60, still works, and makes the next start build a new base, at most once a day. A build that fails is not tried again for 5 minutes: every adb call in every ward would otherwise wait minutes for the same failure, and meanwhile each fails at once with its reason.
- **Ports and serials.** The adb server looks for emulators on console ports 5554 to 5584 when it starts, and learns of others only when the emulator announces itself, which a restarted adb server has missed. Emulators started without a port take the lowest free one from 5554. So Ward's take the highest free even port from 5584 down to 5560: 13 at most, and yours and Ward's meet last. A ward keeps its port, and so its serial (`emulator-<port>`), from one device to its next while `wardd` runs, unless another ward needed the port meanwhile.
- **A ward has its own adb server, and its device is the only one that server can find.** Port 5037 is no longer among the host ports pasta forwards, so the host's adb server, with your phone and every other emulator on it, is out of a ward's reach. Instead `wardd` runs a stock adb server inside the ward, on port 5038, with USB and mDNS off, and while the ward's device runs, the ward's broker listens on the device's two ports (console and adb, the same numbers as on the host) and hands each connection to `wardd`, which connects it to the emulator. An adb server finds emulators by dialing loopback ports, so this one finds exactly one, under the same serial T3 sees. One emulator serving two adb servers at once is supported by the emulator and was tested here: shells, pushes and installs through both at the same time. Emulator ports (5554 to 5585) can't be forwarded host ports, or a ward's server would find the host's emulator there.

  An adb client that finds nothing on port 5037 starts a server there itself. `wardd` doesn't call a ward started until its broker listens there (or 5 s have passed, when something else holds the port), so the ward's first command finds the port taken (measured without that wait: 2 of 6 ward starts whose first command was adb got a server of their own, and an empty device list). It can still happen while `wardd` restarts, or when a ward's broker dies. Every ward's environment sets `ADB_USB=0` and `ADB_MDNS=0`, so such a server is like Ward's: it finds the ward's device and nothing else. But it doesn't start the device, and it holds the port. The broker tells `wardd` when it can't listen on a port; for 5037, `wardd` tells what holds it to exit (adb's `host:kill`) and takes the port, and asks again every minute.
  Nothing has to parse or filter the adb protocol for this, and nothing an adb client does needs rewriting: `adb reverse` and `adb forward` open their listeners inside the ward, where the ward's Metro is and where two wards can't fight over a port; `adb root`, `adb emu`, `adb kill-server` act on the ward's own device and server. It covers the `adb` binary, Gradle's ddmlib, Expo and React Native alike, since all of them talk to port 5037, and none needs `ANDROID_SERIAL`.
- **Lazy.** Every adb client looks for the server on port 5037. In a ward that port is the broker's too: `wardd` gets the connection, reads the client's first request, starts the device if that request is about a device (listing them, picking one, waiting for one; not `adb version`, `adb start-server` or `adb kill-server`), tells the ward's adb server about it, and then connects the client to that server and copies bytes (`src/adb.ts`). So the first `adb devices` or `./gradlew installDebug` in a ward waits about 5 s and then sees a device; a ward that never touches Android never has an emulator. `wardd` starts the ward's adb server the same way, when a connection finds it down. `ward device` does all this from the CLI and prints the serial; from the host, `ward device --worktree DIR` starts the ward first, as `ward desktop` does.
- **Stops when idle, or with the ward.** A device's last use is the latest of: an adb request about a device from the ward, anything the device sent to the ward's adb server (a test run or `logcat` still producing output counts; an open connection that says nothing doesn't, and an idle adb link carries no bytes), `ward device`, and T3's keep-alive (below). The reconciler stops it 15 minutes after that (`WARD_DEVICE_IDLE`), and when its ward stops or is removed. `ward device --keep 2h` moves the last use two hours ahead (at most 4 hours: a kept device is one no other ward can take when all are in use). The next request boots a new instance from the base image: what was installed or changed on the old one is gone. That is the agreed tradeoff; a device per ward that keeps its data is a later phase, if this hurts.
- **Capacity.** A device holds about 3.6 GB of memory while it runs (measured: its unit's anonymous and shared memory) and 8 % of a core idle. At most `WARD_DEVICE_MAX` run (default 8). When one more is asked for, the device unused longest is stopped if it has been unused for 6 minutes, longer than T3's keep-alive interval, so one with an open T3 session is never taken; otherwise the request fails saying so, and adb prints the reason.
- **What T3 needs** (the contract with Annex, which must work unchanged without Ward):
  - `ward devices --json` → `{ "avds": ["ward-base-<key>"], "devices": [{ "serial", "ward", "worktree", "state", "startedAt" }] }`: every serial Ward owns, `state` being `booting` or `ready`, with `ward` and `worktree` always set. It never starts `wardd` and prints the empty shape when it is down. T3 lets a thread open a ward device only when the thread's worktree is `worktree`, names it after the ward, and never boots a `ward-*` AVD.
  - `ward device --worktree DIR --json` → `{ "serial", "state": "ready", "startedAt" }`, once Android has booted. Exit 3 means DIR can't have a ward (it isn't a T3 worktree, or its project isn't enabled) or has one started before wards had devices (T3 falls back to the shared pool); exit 1 comes with the reason on stderr for the agent, its first line saying what failed and the emulator's last log lines after it. T3 calls it when a warded thread opens a device without naming one.
  - T3's Device panel and agent-device talk to the host's adb server directly, so Ward sees none of that traffic. While a live thread has the ward's device open, T3 repeats the call above every 5 minutes, which counts as a use; there is no hold to release, so a crashed T3 leaks nothing. A new `startedAt` (or serial) tells T3 the device it had is gone.
  - T3 may shut a ward device down (the Device panel's power button, `device_close` with `shutdown`), by killing the emulator over adb. Ward treats an emulator that died as stopped: the next request boots a fresh one.

T3's device daemon (`agent-device`) binds a random port each start, and its CLI dials 127.0.0.1 at the port in T3's `daemon.json`: `wardd` watches that file and has each ward's broker listen on that port inside the ward, handing every connection to `wardd`, which connects it to the host's port (the mapped-port path reversed). The socket scan skips the ports the broker listens on and the ward's adb server, so none is mapped back out.

Decided against:

- **Filtering the host's adb server** (`wardd` in front of port 5037, passing only requests for the ward's serial and answering `adb devices` with one line). It was written first. It needs a parser for every way adb names a device, and a miss is a hole: a connection that has picked a device can still send another host request, `adb reverse` makes the server dial the host's loopback, `adb root` picks by transport id. `adb forward` would have had to be refused, and `adb reverse` rewritten. With a server per ward the isolation is the network namespace's, and the only request `wardd` reads decides nothing but whether to boot.
- **Filtering in the `adb` shim.** It covers only programs that run the binary. Gradle's `installDebug` and `connectedAndroidTest` speak the adb protocol to port 5037 themselves and act on every device listed.
- **The emulator inside the ward.** Isolated by construction, but its ports would be in the ward's network namespace, where the host's adb server, and so T3's Device panel, can't see it.
- **Renaming the device inside the ward** (always `emulator-5554`). T3's tools name it by its real serial, so an agent would see two names for one device.
- **A grant for the shared devices or your phone** to a ward. A warded agent drives those through T3's device tools, which run on the host. Annex didn't need more.
- **A memory check instead of a count.** What is free changes by the minute here and the machine has swap; a refusal on a guess would stop an agent that could have run.
- **Hold and release calls for T3.** A keep-alive that is just the start call again needs no cleanup when T3 crashes. Its cost: a keep-alive that arrives after the device was shut down starts a new one, which then idles out.

Limits:

- A ward started before this keeps pasta's forward of 5037: its adb still reaches every device on the host, the `adb` shim still does for it what it did (starts the host's server through `wardd`, rewrites `adb reverse`), and it has no device of its own, until it is stopped and started. `ward device` says so and exits 3. The shim's old half goes once no such ward is left.
- The isolation is against accidents, as everywhere in Ward. A ward command that sets out to can still start a second adb server with USB on, or `adb connect` a device on your network: wards see `/dev/bus/usb` and your adb key (`~/.android/adbkey`), which your phone trusts. Every adb server started in a ward has USB and mDNS off unless it is told otherwise, so no ward lists such a device unasked. Your AVDs (`~/.android/avd`) are an empty folder in a ward, so an emulator started there can't run from the disks of T3's shared ones.
- Port 5038 and the device's two ports are taken inside the ward while it has a device. A program in the ward that binds one of them first (an emulator of its own) keeps the device from being found.
- Every ward device is the same hardware and system image, the template's, and the same Android: one snapshot, so the same Android ID and accounts state in each. A project that needs another API level uses T3's shared devices through its device tools.
- A device's data lasts as long as its emulator. An idle stop in the middle of a long manual session loses what was installed; `--keep` is for that.
- A program on the host with your uid can still drive any emulator through the host's adb server, and one that acts on every device listed does: `./gradlew installDebug` or `connectedAndroidTest` run outside a ward (a project without wards, a main checkout, a T3 thread with no ward) installs on every ward's device too, as it does on T3's shared ones. T3 refuses a ward's device to other threads; for host builds, `ANDROID_SERIAL` is what keeps them to one device.
- adb in a ward must be the SDK's (`$ANDROID_HOME/platform-tools/adb`, which is what `adb` on the ward's `PATH` is): the ward's server is that version. A client of another version (a distribution's `/usr/bin/adb`) tells the server to exit and can't start its own, each time it runs.
- When `wardd` restarts, adb connections through it are cut, as mapped ports are, so an install or test run in a ward at that moment fails and works when run again; the ward's adb server finds its device again within a second or two, and the device itself keeps running. The host's adb server is not `wardd`'s to stop: when `wardd` finds none it starts one in a scope of its own, outside its unit.
- T3 gives its own emulators a camera image per serial (`-camera-back imagefile:…`); ward devices have the template's emulated camera.
- The emulator's gRPC port is not relayed into the ward.

## Desktops

Goal, in the words of the request (2026-11-19): "give each ward its own headless Umbriel desktop, so parallel agents can drive and verify GUI apps with Puck without fighting over my one live session and cursor. […] Apps the agent launches open there, and Puck's tools […] act on that desktop instead of mine. My live session stays the default when there's no ward, or when the agent explicitly asks for it. […] A per-ward instance must not steal or disturb my live session's bus names, notifications, portals or audio. […] start the desktop lazily on first use, stop it with the ward, and make it reachable from agent commands inside the ward."

A ward's desktop is three things in one folder, `$XDG_RUNTIME_DIR/ward/<id>/desktop`, which is the desktop's own `XDG_RUNTIME_DIR` under the short name `$XDG_RUNTIME_DIR/ward/d<pid>`:

```
ward "indexio/t3-d7059d66…"                         host
┌───────────────────────────────────────────┐      ┌──────────────────────────────┐
│ dbus-daemon (the desktop's session bus)   │      │ Puck's MCP server            │
│  └ at-spi-bus-launcher, at-spi2-registryd │◀─────┤  asks `ward desktop` for the │
│ umbriel, headless: HEADLESS-1 1280×720    │ unix │  env, then runs umbriel,     │
│  └ apps: `ward desktop -- CMD`,           │ sock │  grim and AT-SPI with it     │
│    Puck's launch_app                      │      │ live Umbriel + Noctalia:     │
└───────────────────────────────────────────┘      │  never contacted             │
                                                   └──────────────────────────────┘
```

- **A session bus of its own.** Everything a desktop shares with the live session goes through the session D-Bus and `XDG_RUNTIME_DIR`: bus names, notifications, portals, the tray, single-instance apps (a GTK app started on the live bus hands its window to the instance already running on your screen), the accessibility bus, PipeWire's socket, and Umbriel itself, which publishes `WAYLAND_DISPLAY` and `UMBRIEL_SOCKET` into the systemd user manager over that bus when it starts. So the desktop gets a `dbus-daemon` whose config lists one service folder holding one file, the accessibility bus, started with accessibility on. Nothing else can be activated on it: no portal, keyring, notification daemon or dconf writer. With no systemd in its runtime folder, Umbriel's publish step finds no manager to talk to, and the only PipeWire socket there is the desktop's own (below).
- **Umbriel, headless.** `WLR_BACKENDS=headless umbriel -c <its own config>`: no autostart, so no Noctalia shell, bar or notifications, and none of your keybinds. It makes one 1280×720 output, `HEADLESS-1`; `ward desktop -- umbriel output-create NAME 1920x1080` adds more. Umbriel writes its log under `XDG_CACHE_HOME`, which would be your session's log, so the compositor gets a cache folder in the ward's own `TMPDIR`.
- **A keyboard.** A headless compositor has no input devices, and an app listens for keys only while the seat has a keyboard. `wtype`, which Puck types with, brings a keyboard for each press and takes it away again, so an app got a key only if it noticed the keyboard in time: typing `abcdefgh` arrived as `abe`, `abceg`, `bcdeh`. The desktop therefore holds one keyboard for as long as it runs (a sleeping `wtype`), and all eight keys arrive every time.
- **Short paths for sockets.** A socket's path must fit in 108 bytes, and a ward's runtime folder is long (`…/ward/<repo>.<worktree>/desktop` is 57 bytes plus the repo's name). So the desktop's `XDG_RUNTIME_DIR` is a short link, `ward/d<number>`, and its `TMPDIR` the link `d<number>/tmp` to the ward's own. `wardd` makes a ward desktop's link, since Ward's runtime folder is read-only inside the ward: a random number above any pid (`d9` and nine digits), so it never meets the `d<pid>` a thread's desktop names itself after. The name is new at every start, and not the ward's slot, which passes to another ward: a command that had read an earlier desktop's name would otherwise act on a later one, this ward's or another's. A name goes when its desktop exits (`wardd` removes a ward desktop's when the process it started ends), when the ward's next one starts, and when the ward stops. Chromium keeps a socket under `TMPDIR` and aborts at start when the path is too long, which the ward's is.
- **Inside the ward.** `wardd` starts it through `ward exec --running`, so it runs in the ward's namespaces and cgroup; `--running` fails where plain `ward exec` would start the ward or run the command unwarded, so a ward stopped or a project disabled at that moment can't put the desktop anywhere else. Apps the compositor starts (Puck's `launch_app`) are therefore in the ward too, start in the worktree's folder and reach the ward's `localhost` ports, and stopping the ward stops the desktop with everything on it. Its sockets are path sockets under the host's `/run/user`, so tools on the host connect to them like any others.
- **Sound of its own, with Caliban.** With no PipeWire socket in its runtime folder, apps on the desktop find no sound server and play nothing. When [Caliban](https://github.com/Axl47/caliban) is installed (`caliban` on PATH), `ward-desktop` starts `caliban audio serve` once the session bus is up: a PipeWire and WirePlumber with one null sink, no hardware and no saved state, their sockets in the desktop's runtime folder, so apps there play into a sink an agent can record and nothing reaches your speakers. An app picks its sound server when it starts, so the desktop publishes `env` only once the server is ready, waiting as long as the server is alive and not ready, at most 3 s (about 0.3 s measured; `wardd` gives the desktop 8 s in all); a server that fails to start leaves a warning in `desktop.log` and a desktop without sound, as before. It stops with the bus. Without Caliban nothing changes.
- **Accessibility.** `at-spi-bus-launcher` runs the accessibility bus with `dbus-broker` when it can, and `dbus-broker` starts services through systemd, which the desktop doesn't have. So the registry (`at-spi2-registryd`) is started with the desktop rather than on demand; without it apps never register and Puck's `inspect` falls back to OCR.
- **App profiles of its own.** The ward shares your home folder, and a Chromium-family browser or an Electron app hands a launch to the copy already running on its profile, wherever that copy's window is. Measured: Helium started on ward B's desktop with the profile in use on ward A's opened its window on A's, and a single-instance Electron app started in B handed off to A's and showed nothing. With your profile that is your screen, or, if the ward's copy started first, your next window opening on a desktop you can't see. An Electron app's profile is `$XDG_CONFIG_HOME/<name>`, and one that sets the path itself ignores `--user-data-dir`, so the folder is what has to differ. The desktop's `XDG_CONFIG_HOME` is therefore a mirror of yours in the ward's `TMPDIR`: folders of its own, holding a link to each of your files. Programs read your settings (`git`, `gh`, fonts, an app's flags file), and whatever they create stays in the ward, so an app first started there makes its profile there, also where your folder for it already exists but was never used (Omarchy ships `google-chrome/` and `obsidian/` like that). Folders that already are a profile, with Chromium's `Local State` or Firefox's `profiles.ini` at most one folder down, are left out, so those apps start fresh as well. The mirror is redone at each desktop start (50 ms for 1,000 entries). A fully private config folder was the alternative; it takes git's identity, fonts and every tool's settings from the prefixed command, or needs a list of which to keep.
- **Lazy.** Nothing runs until the first `ward desktop`, which asks `wardd` to start the ward if needed and then the desktop, and waits until the compositor is up and the registry is on the accessibility bus: 0.4 s in all, and about 70 MB of memory (PSS) while it runs, nearly all of it Umbriel. `bin/ward` answers later calls itself from the desktop's `env` and `pid` files, without Node, in 8 ms, after checking them (below). Its output, and that of every program the compositor starts, is appended to `desktop.log` in the ward's data folder, on disk rather than in `/run/user`, which is small and shared with your session.
- **Files it checks.** The desktop's folder is under `$XDG_RUNTIME_DIR`, which every program of yours can write, so `bin/ward` (`ward_desktop_read`) takes nothing there on trust before printing or using a desktop: `pid` must name a live process of the desktop's own unit (`ward@<id>.service` for a ward's, `ward-desktop-<id>.service` for a thread's), `env` may hold only the names `ward-desktop` writes, each pointing into that desktop's own folder through a short name (`d<digits>` resolving to it), and the sockets it names must be sockets of that folder, neither symlinks nor hard links, either of which would reach another server. A ward's desktop writes its pid as the ward's PID namespace sees it, so from the host it is looked up in the ward's `/proc` through the ward's namespace holder (the ward's `pid` file), once that holder is shown to be a process of the ward's unit in another PID namespace; inside the ward, `/proc` is the ward's own. It costs no measurable time. `wardd` makes the same process check before it counts a desktop as up, and clears the folder of one that fails. Before this (red team, 2026-11-20), two files any agent could write, a `pid` naming any live process and an `env` naming your session's sockets, made Puck call your live session a thread's private desktop and drop its live-session guards. What it doesn't stop: a program that means to can still name another thread's id (`T3CODE_THREAD_ID`) and reach that thread's desktop, or move a process of its own into a desktop's unit; telling one of your processes from another takes more than one user id.

### How a command gets on it

One rule, the usual Wayland one: a process is on the desktop its environment names (`XDG_RUNTIME_DIR`, `WAYLAND_DISPLAY`, `UMBRIEL_SOCKET`, `DBUS_SESSION_BUS_ADDRESS`). `ward desktop` prints the ward desktop's, and `ward desktop -- CMD` runs `CMD` in the ward with it, after unsetting what could still point at your session (`WAYLAND_SOCKET`, `AT_SPI_BUS_ADDRESS`, PulseAudio's and PipeWire's overrides). Where there is no ward, the desktop is the calling T3 thread's own (below); with neither it exits 3 and runs nothing: `ward exec` falls back to running the command unwarded, but a command sent to a private desktop must not open on yours instead.

Puck is the one program that picks for itself, because driving your screen by accident is the collision this exists to end. Its MCP server (one process outside the ward for the whole thread) and its CLI in an agent's shell both ask `ward desktop` and act on the answer; `desktop_state` with `desktop: "live"`, or `PUCK_DESKTOP=live` for the CLI, moves them to your screen. Each tool call is given its desktop once, when it starts, so a switch made by another call can't move half of it. If `ward desktop` fails, Puck reports that and never falls back to your session.

Decided against:

- **Putting the desktop in every ward command's environment**, so a bare `cargo run` would open there. The ward's commands would then lose the live session bus, and `gh` keeps its token in the keyring on that bus (`gh auth status`: "keyring"), as does `git push` through it. A GUI app half in (ward's Wayland socket, live bus) is worse: its notifications, tray icon and single-instance hand-off land on your screen.
- **Making un-prefixed GUI launches fail in a ward**, by pointing `WAYLAND_DISPLAY` nowhere. Miranda, the first warded project, watches the live session on purpose and finds it through the one socket in `XDG_RUNTIME_DIR` when `WAYLAND_DISPLAY` is unset. So a GUI program started in a ward without the prefix still opens on your screen, as before.
- **A Noctalia shell on the desktop.** It claims bus names and talks to NetworkManager, logind and PipeWire, and an agent checking an app needs none of it. Puck's notification and shell-setting tools say so on a ward's desktop.

Limits:

- Under `ward desktop --`, `XDG_RUNTIME_DIR` is the desktop's folder, so that command has no keyring, `systemctl --user` or gpg-agent, and sound only into the desktop's own server when Caliban is installed; start the app with it, and build, commit and push without it.
- A plain `ward exec` command keeps the host's `XDG_RUNTIME_DIR`, so a program it starts that plays sound still plays through your session's PipeWire and out of your speakers; only apps on the desktop reach its own server. A follow-up: a sound server per ward that `ward exec` points its commands at too. (`$XDG_RUNTIME_DIR/ward` links back to Ward's own runtime folder, so `ward` still works there.)
- Your home folder is shared, and only the config folder is mirrored: an app that finds its running copy through other files, not the session bus, still hands its launch to that copy, such as a Firefox whose profile is under `~/.mozilla` (it refuses to start a second copy rather than moving it; give it `--profile DIR`), or an app with a socket or lock under `~/.local/share` or `~/.cache`, as Zed has (`~/.local/share/zed/zed-stable.sock`; not tried, but its launches would go to the copy on your screen). A program that rewrites one of your existing config files in place changes yours, as it does outside a ward, and an app's data elsewhere in your home folder is yours too.
- No Xwayland: it refuses `/tmp/.X11-unix`, whose owner (the host's root) is nobody inside the ward's user namespace. X11-only apps don't run on a ward's desktop, and `DISPLAY` is empty there so they can't reach your session's instead.
- Programs the compositor starts (`launch_app`) get Ward's service environment, not your shell's: a program that needs your shell's `PATH` starts with `ward desktop -- CMD`.
- Typing needs `wtype` installed, for the keyboard above.

### Threads without a ward

Goal, in the words of the request (2026-11-19): "add a way to launch test applications or windows […] in a way that gets routed to silent space so I don't see it. […] some agents using the tools that we have right now, even with this update, they sometimes make the window visible for me. So having a standard way of opening things for testing that is handled maybe in one command […]. If a thread is running without a ward, like projects in omarchy-config, that simple open command can just take care of that setup and giving the agent their own test desktop […] instead of having to think about that isolation themselves", and the command should give "a quick way to interact with the things in their desktop […] they wouldn't need to know ahead of time the window ID, the place where they are at, the desktop ID."

Only projects enabled for Ward have wards (one, when this was written), so every other thread's GUI checks landed on your screen. Now `ward desktop -- CMD` works in any T3 thread: where the folder has no ward, the desktop belongs to the calling thread.

```
                          in a warded worktree            anywhere else in a T3 thread
ward desktop -- CMD       the ward's desktop,             the thread's desktop, started if needed;
                          started if needed; CMD          CMD runs in no namespace, in the
                          runs in the ward                desktop's cgroup
ward desktop  (prints)    starts it, prints               exit 3 until the thread's first command
                                                          on it; from then on starts it, prints
stops                     with the ward                   when the thread settles, is archived or
                                                          deleted, or after 2 h unused; unknown
                                                          to T3: 30 min unused. The next call
                                                          starts it again, empty
```

- **Whose it is.** T3 gives every agent's shell and MCP servers `T3CODE_THREAD_ID`. The desktop's id is `t-<that id, sanitized>`: no dot, which every ward's id has, so the two never share a folder under `$XDG_RUNTIME_DIR/ward`. A delegated child is its own thread and gets its own desktop; subagents inside one thread share one. The folder is not the key, as it is for wards: threads without a worktree share their project's folder, and a second thread there, working on your real desktop on purpose, would find Puck on the first one's.
- **The same desktop, in no namespace.** `wardd` runs the same `libexec/ward-desktop` as a transient unit, `ward-desktop-<id>.service`, under the wards' slice: its own session bus, headless Umbriel, accessibility, keyboard, short socket names and mirrored config folder, all as above. Its caches, app profiles and log are in `~/.local/state/ward/desktops/<id>` and go when it stops. There is no network namespace, because the thread's dev servers aren't in one: a browser on the desktop reaches `localhost:5173` as the thread does.
- **A command starts it; asking does only afterwards.** `ward desktop -- CMD` starts the desktop (0.4 s) and runs `CMD` after moving it into the unit's cgroup, so stopping the desktop stops what was opened on it. The cgroup is read from the desktop's own process (`/proc/<pid>/cgroup`), so there is no second file a command could arrive before. Plain `ward desktop` exits 3 for a thread that never ran a command on its desktop: Puck asks before every call, and such a thread is on your screen on purpose (a task about your real desktop). The first start leaves a marker, `~/.local/state/ward/desktops/<id>/thread`, and from then on plain `ward desktop` starts the desktop again whenever it is down. Without that (the first build), a desktop that stopped or crashed made the next ask answer "none", and Puck went back to your screen in the middle of the thread's test, silently; three reviews found it.
- **Stops with the thread, or when idle.** The reconciler applies the wards' rule (`shouldStop`) with the one thread as the desktop's threads: it stops once the thread is settled, archived or deleted and wasn't used since, or 30 minutes unused when T3 doesn't know the thread. An active thread's desktop also stops after 2 hours with no call and no typing in a terminal on it (`DESKTOP_IDLE_MS`), since long threads otherwise keep one for days; unlike a ward, it holds no services worth keeping up. Stopping removes what apps kept there; the marker stays for good, so the next call brings back an empty desktop, which `desktop_state` shows, and plain `ward desktop` never exits 3 again for a thread that once had a desktop. The last log stays until T3 doesn't list the thread and 30 minutes have passed since the desktop's last use (the marker's time, set as its runtime folder goes), never in the pass that stopped its desktop or cleared a dead one. The marker used to go with the log, and Puck was then back on your screen for the rest of the thread; a red team (2026-11-20) found that this was the common case, not a corner: a thread missing from the list Ward reads may be very much alive, because another T3 server (the desktop app's own, a dev server) runs it, and T3's list leaves out archived threads that can come back. A marker is a few bytes per thread that ever opened a desktop. Desktops are found by their folders, so there is no registry entry and no slot, and a restarted `wardd` picks them up. One whose compositor died is cleared away on the next pass, and a failure on one doesn't stop the pass for the others.
- **A thread of a warded worktree gets that ward's desktop from any folder.** An agent's shell can stand outside its worktree (a `cd` to a scratch folder) while its Puck server stands inside it. The first install showed what that did: `puck open` from the other folder put the window on the thread's own desktop while Puck's tools looked at the ward's, and nothing said why the window was missing. T3's thread list names each thread's worktree, so `wardd` writes a note per thread whose worktree has a ward (`~/.local/state/ward/thread-wards/<id>`: the worktree, then the thread's id), on every reconcile pass and when a thread asks for a desktop of its own before the first pass has seen it. `bin/ward` only reads it: a call by that thread from a folder without a ward goes to the ward's desktop, the command into the ward. `wardd` is the only writer, takes T3's lists one at a time so an older one never undoes a newer one's note, and removes a note only once T3 no longer lists the thread with that worktree. If the worktree is gone or its project no longer enabled, the note stays and the thread gets a desktop of its own even on a plain ask, since it was private before; a thread T3 moves off its worktree, or stops listing, gets a thread desktop's marker in the note's place, for the same reason, and keeps it. Not covered: a plain ask from outside the worktree in a thread's first minute, before a pass has written its note, answers "none" once; and with T3 unreachable a new thread gets a desktop of its own.
- **One command for agents.** Puck's `puck open CMD` is the agent-facing form: it runs `ward desktop -- CMD` detached, waits for the command's window and prints it (id, app, title, geometry) with the command's pid and log. That is the "one command": the agent needs no desktop or window id beforehand, and doesn't have to background the command itself. Puck's `launch_app` starts the desktop the same way (`ward desktop -- true`).

Decided against:

- **A private desktop by default in every thread.** Threads in projects like omarchy-config are often about your real desktop; Puck there must keep looking at it until the agent opens something of its own. It is one condition in `ward_thread_desktop` (drop the marker test) if that default should flip.
- **Starting it from plain `ward desktop`.** Puck's MCP server asks on every call in every thread; each would then get a compositor it never uses.
- **A network namespace for the opened app,** as in a ward: it couldn't reach the unwarded thread's own `localhost` ports.
- **Making GUI launches on your session fail for agents.** Nothing here can stop an agent that sets `WAYLAND_DISPLAY` itself, and some tasks need your screen. Puck covers its own door: `launch_app` opens on the private desktop unless the agent asked for the live session. The global agent instructions name `puck open` as the way to open anything for a check.
- **Guessing the thread from the folder** where a caller has no `T3CODE_THREAD_ID`: several threads share a folder, and a wrong guess hands one thread another's windows.
- **Listing thread desktops in `ward ls`.** T3 polls that list for wards. `systemctl --user list-units 'ward-desktop-*'` shows them, and the idle stop bounds what a missed one costs.

Limits: all those of a ward's desktop. Outside T3 (no `T3CODE_THREAD_ID`) and outside a ward there is no private desktop. Codex gives its MCP servers no `T3CODE_THREAD_ID` (measured 2026-11-19: one `codex` process serves several threads), so Puck's MCP tools there stay on the live session, where they refuse to open or press anything, and the thread's shell drives its desktop with the `puck` CLI; passing the id to MCP servers is a change for T3. Thread ids are sanitized into the desktop's id, so two ids differing only in characters outside `[A-Za-z0-9_-]` would share one; T3's are UUIDs or `mcp:`-prefixed hex.

Verified in a second Ward instance (2026-11-19): a thread's first `ward desktop -- true` took 0.39 s; `puck open foot` returned the window in 0.8 s; two threads' desktops each showed only their own windows; the opened program was in the desktop unit's cgroup; a reconcile pass stopped the desktop of a settled thread and of an unknown thread unused for 31 minutes, removed their folders and short names, and kept an active thread's.

## Lifecycle and teardown

| Event | Ward action |
| --- | --- |
| First command in a worktree (lazy) | `up`: create namespaces, unit, slot, Podman service |
| Every thread on the worktree settled, and the latest settled after the ward's last start, command, or terminal input, or none of those for 30 minutes | `stop`: kill processes (open terminals included) and containers, release host ports; keep volumes so the next command resumes |
| No active thread on the worktree (its threads were archived or deleted) and no command for 30 minutes | `stop` |
| Worktree removed | `rm`: move the ward's data, including the container store and volumes, to a trash; it comes back if the same worktree reappears within 7 days, then it is purged. `ward rm` also uses the trash; `ward rm --now` deletes at once |

`wardd` runs a reconciler every minute, plus within about two seconds of a change in a warded repo's worktree folder. It reads thread state from T3's orchestration API (`GET /api/orchestration/shell`) with a read-only `orchestration:read` token in `~/.config/ward/t3-token`, and applies the table above. T3's list leaves out archived and deleted threads, so those count as "no active thread". Deleting a thread only stops its ward, because the worktree, and so the work, may outlive it; only a worktree that is gone removes data, and only while the worktrees folder itself exists. If T3 is unreachable, nothing is stopped. Each ward's last start and last command are kept as file times, so restarting `wardd` doesn't reset them. A stop costs little: the next command starts the ward again, though services must be restarted (compose `restart:` policies don't apply). When all 99 slots are taken, a new ward takes the slot of the stopped ward unused longest, and that ward gets a new slot and new host ports when it next starts. The reconciler also re-attaches port mapping for running wards whose broker died.

## Activity records

A recorder on the host (Miranda's Mneme) can ask `ward exec` for a record of each agent command, to profile how agents work: what they run, how long it takes, what fails.

- **The folder** is `$XDG_RUNTIME_DIR/ward/activity`. wardd creates it at start, mode 0700, and every ward's mount namespace covers it with an empty read-only folder (`libexec/ward-init-root`), so a process in a ward can't read another thread's commands there or forge a record. A ward started before the folder existed still sees it (read-only), so each ward notes that it hides it (`activity-hidden` in its runtime folder, which the ward can't write), wardd's `/ls` reports it as `activityHidden`, and a recorder must stay off while any running ward lacks it. Restart such wards to record.
- **On and off** is the recorder's: it keeps `activity/on` fresh, the file's first word being the time it was last written in epoch seconds, good for 30 s. A recorder that dies switches recording off by not writing.
- **What is recorded**, only while on and only for a caller with a `T3CODE_THREAD_ID` (an agent; your terminals have none): when the command starts, `activity/exec.<pid>.<time>` with when `ward exec` was called, when the command started (the difference is a ward that had to start), the caller's cgroup, its thread, the ward, the folder, `CLAUDE_CODE_SESSION_ID` and the argv, each argument cut to 4000 characters; when it ends, `<same>.end` with the exit status, the time and the shell's `times`. Fields end in a NUL. The command's output is never recorded. The recorder deletes the files as it reads them.
- **How.** The record needs the exit status, so while recording `ward exec` runs `nsenter` as a child instead of becoming it (`bin/ward`: `ward_record_run`). The caller must not notice: the child keeps stdin and the default SIGINT and SIGQUIT, TERM, INT and HUP sent to the wrapper are passed on, and a wrapper killed outright takes the command with it (pdeathsig). One difference remains: a command that died of signal N ends the wrapper with exit status 128+N, where `exec` would have died of the signal itself; a shell can't tell that apart from a command that exited 128+N. With recording off, `ward exec` is the same `exec` as before. It needs bash as `/bin/sh` (for `$EPOCHREALTIME`); under another shell nothing is recorded.

## The Annex change

Ward needs no lifecycle hooks from T3: wards start lazily on the first command, and the reconciler handles stop and removal. So the Annex change is only the process wrapping, behind one env var, `T3CODE_WARD_COMMAND` (the `ward` executable), in a new `apps/server/src/ward/Ward.ts` with one-line seams:

- Claude gets `CLAUDE_CODE_SHELL_PREFIX=ward-prefix`. Claude Code runs MCP servers, hooks and LSP servers through the same prefix, so `ward-prefix` sends only Bash tool commands (the ones that source a shell snapshot) into the ward. The Claude process, its API traffic and MCP stay on the host. If Claude Code stops using shell snapshots, its commands silently run on the host again.
- Codex runs one app-server per thread, but its commands go through `bash -c`, so it gets `BASH_ENV=ward-bash-env`, which re-runs the command in the ward when the working folder is a warded worktree. Inside Codex's own sandbox (its non-full-access modes), which has its own namespaces and can't reach `wardd`, the hook leaves commands alone.
- Integrated terminals are launched as `ward exec --worktree <cwd> -- <shell>`.
- The port scanner replaces `wardd`'s host sockets with one entry per ward port, attributed to the worktree's thread.

Every hook passes through untouched for folders that aren't warded worktrees, so non-worktree threads and projects without `ward enable` behave as before.

## Code shape

TypeScript on Node 26 (run directly, no build step), one package: the `ward` CLI and the `wardd` user daemon. Node's IPC can pass socket handles between processes, which covers the fd broker without native code, and `node:ffi` reads a caller's credentials from the control socket. `ward exec` is a small POSIX shell script on the hot path (cgroup move + `nsenter`), since it runs on every agent command.

System changes on gaia-arch, recorded in omarchy-config: install `podman`, `passt` and `crun`; subuid/subgid ranges for the user; enable `wardd.service` (user unit).

## Risks and limits

1. **Podman as root inside a custom user namespace** worked, with cgroups disabled, crun, file event logging, and a private `/run`.
2. **`sudo` doesn't work inside a ward** (setuid binaries can't run in a user namespace). Wards are opt-in per project (`ward enable <repo>`), so projects that need system changes simply don't enable them.
3. **Codex** runs one app-server per thread, but wrapping the app-server would put its API traffic and MCP in the ward too, so the `BASH_ENV` hook wraps its commands instead.
4. **Ward's view of T3.** Ward serves `~/.t3` (or `WARD_T3_HOME`), not `T3CODE_HOME`, which T3 dev servers point at their own state. Ward follows T3's `worktreesDirectory` setting (absolute paths only), read on every call, and keeps counting `~/.t3/worktrees` so worktrees made before the setting changed keep their wards; a folder the setting pointed at before is dropped when it changes again. Only folders outside `~/.t3/worktrees` pay for reading the setting, one `sed` per agent command.
5. **Processes leave T3's per-thread scope.** Ward commands move into the ward's unit, so T3's thread kill no longer reaches dev servers an agent started; stopping the ward does.
6. **Devices** hold about 3.6 GB each, under the agents' memory limit: eight of them, the default cap, are half of it. The cap is a count, not a measure of what is free.
7. **`XDG_RUNTIME_DIR` is shared** between wards and the host, since Wayland, PipeWire and the keyring's bus live there; only the systemd manager and the raw session bus are hidden, and Ward's own folder is read-only. Two worktrees of an app that keeps a pid file or socket there collide; such files belong in `TMPDIR`, which is per ward. Ward's own files there are checked before use ("Files it checks").
8. **What a ward command acting deliberately can still do to the host.** Closed: the systemd user manager and session bus, `wardd`'s API beyond the ward's own calls, Ward's own state and config, Ward's and T3's credentials, other processes. Open, each because the design relies on it or closing it is a project of its own:
   - *Your live session.* The compositor's IPC socket runs commands (`umbriel msg spawn`), and any Wayland client can type into the focused window through the virtual-keyboard protocol (as `wtype` does) or drive apps over the accessibility bus. Ward keeps these: GUI apps started in a ward open on your screen, Miranda's worktrees watch the live session, and `PUCK_DESKTOP=live` drives it from an agent's shell. Hiding them means a runtime folder that lists what a ward may reach, and breaking those.
   - *Your home folder is writable*, as the same uid. A ward can put code where the host later runs it: shell startup files, `~/.config/systemd/user`, `~/.local/bin`, git hooks of a main checkout (a worktree's `.git` lives there), any project's scripts. Closing that is a read-only home with a list of what stays writable (worktree, caches, git's common folder, ...), which every toolchain would have to fit.
   - *One subuid range for all wards.* Every ward's container root is host uid 100000, so ownership alone doesn't separate their stores; only the mount namespace above does. Container processes of two wards can't signal each other because Podman requires a private PID namespace when cgroups are off (`--pid=host` is refused, measured). A range per ward (slot N mapping its own 65536 ids) would add ownership as a second wall, but needs a wider range in `/etc/subuid` (root), and the shared image store's files would then show as nobody in every ward but one (so overlay copy-up of them would fail; reasoned, not tried), so that store would have to become per ward or move behind idmapped mounts, which btrfs allows only to root.
   - *Processes.* A ward no longer sees or signals other wards' or the host's processes (PID namespace). The host still sees every ward's.
   - *Other runtime sockets* (gpg-agent, the keyring's SSH agent, PipeWire) stay reachable, and the keyring through the proxy gives out every secret it holds, as it does for `gh`.

## Verification

Three Claude subagents in three real T3 worktrees of a small test app, in parallel: each starts a dev server on the same port, `docker compose up` Postgres on 5432, writes a row, and checks it reaches its own services. Pass means: no port errors, each sees only its own row, each ward's dev server answers on its own host port, `ward rm` leaves no processes, containers or ports behind, and the reconciler cleans up a worktree removed by hand.

Desktops, verified in a second Ward instance (2026-11-19) by four agents working at once, each in its own ward, through Puck's MCP server and CLI: the first call started the ward and its desktop (0.35–0.45 s; 9–10 ms afterwards); each ward saw only its own windows, of the same GTK app (one application id) and of foot and Evince; `screenshot`, `inspect` (accessibility text), `launch_app`, `focus_window`, `move_window`, `arrange_windows`, `switch_workspace`, layout snapshot and restore, pointer clicks and typed keys acted on the caller's desktop; six simultaneous first calls made one compositor; killing the compositor took its bus and apps with it and the next call started a fresh one; `ward stop` left no process or folder; `notify-send` and `pactl` found no service; and the live session's windows, focus, bar, notifications, bus names, accessibility apps and systemd environment were the same before and after. Helium opened on each ward's desktop with that ward's profile, and a single-instance Electron app got a window in each of two wards. Not exercised: a second output, and anything under Xwayland (there is none).

Verified since, with real T3 threads building a real project in parallel wards (2026-11-19): a settled thread's ward stopped 4 seconds after the settle; a merged thread's worktree removed by T3 sent its ward to the trash within seconds; Wayland screenshots, PipeWire recording, the accessibility bus and the GPU all work from inside a ward. 

Verified for devices, in a second Ward instance beside the installed one (2026-11-22): the first device built its base image and booted in 45 s, later ones in 4 to 6 s from the first adb command; two wards each listed only their own serial and got `device 'emulator-…' not found` for the other's and for the shared `emulator-5554`; `adb reverse`, `adb forward`, `adb emu`, `adb root` and `adb kill-server` worked unchanged; push ran at 650 MB/s and pull at 330 MB/s through the ward's relay, the same as on the host (and 16 MB/s before the relay set `TCP_NODELAY`, which mapped ports now have too); `adb version` and `adb start-server` booted nothing; a device with an open but silent adb connection stopped after the idle time while one with a shell still printing kept running; killing an emulator from the host (`adb emu kill`, as T3's power button does) was followed by a fresh device with a new `startedAt` and none of the old one's files; a third device over a cap of two was refused with the reason in adb's output; `ward stop` took the ward's device with it, also 2 s into its boot (the stop returned in 0.2 s and the emulator was gone), and a ward stopped and started at once got a fresh device; running devices were taken up again across several `wardd` restarts; Gradle's `installDebug` (ddmlib, no `adb` command first) booted the device and installed, and did so again after the device was stopped under a living Gradle daemon, after `adb disconnect` and after `adb kill-server`; an adb server started on a ward's port 5037 while its broker was gone was told to exit when the broker came back, and a web server there was left alone until it exited; a base build made to fail ran once, and later adb calls failed in under 0.1 s with its reason; a new ward's `~/.android/avd` was empty and read-only; and while a base image built, the host's adb server never listed it, and the adb server its emulator started was gone when the build ended (in two of three builds that server listed only the base image; in the third it also listed the three emulators started outside Ward, though not the phone or another ward's device, for a reason not found; nothing but the build's own emulator talks to it). Not run: a snapshot that doesn't load, an emulator that survives its unit's stop, the host's adb server being started by `wardd` (that needs it stopped, and other threads were using it), and a ward started before this change answering `ward device` with exit 3 (only the installed Ward has such wards).
