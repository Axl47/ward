# Agent notes

- The installed Ward runs from the main checkout; test a worktree's code with a second instance, never by restarting the live `wardd`: export `XDG_STATE_HOME`, `XDG_CONFIG_HOME` and `XDG_RUNTIME_DIR` pointing at private folders plus `WARD_UNIT=<name>`, install a `<name>@.service` copied from `units/ward@.service` (with `@WARD_HOME@` and `@NODE@` filled in) with those three variables as `Environment=`, and run this checkout's `src/daemon.ts` (e.g. `node src/daemon.ts &` with the same environment; with `WARD_UNIT` set, `bin/ward` never starts a daemon itself) and `bin/ward` with the same environment.
- `WARD_UNIT` exists only from PR #2 on, and only from the commit that added this line does `bin/ward` stop starting the installed `wardd.service` when it is set: never run an older checkout as a second instance, since it starts units under the live `ward@` template or the live daemon.
- With a private `XDG_RUNTIME_DIR`, symlink `systemd` and `bus` from `/run/user/<uid>` into it, or `systemctl --user` fails; keep it short (e.g. `/run/user/<uid>/<name>`), since Podman's socket path inside it must fit in 108 bytes.
- A second instance's registry starts at slot 1 like the live one; seed it with placeholder records for low slots so its host ports don't take ones live wards will want. Each placeholder's `worktree` must be an existing folder under the instance's `WARD_T3_HOME` worktrees, or the first reconcile removes the record and frees its slot.
- A thread's desktop (no ward) runs as the transient unit `<WARD_UNIT or ward>-desktop-<id>.service`, so a second instance needs no unit installed for it; `wardd` passes it its own `XDG_*` folders. Stop a test instance's with `systemctl --user stop '<name>-desktop-*'`.
- Stop a test `wardd` by pid, found by its arguments and folder (`ps -eo pid,args | awk '$2=="node" && $4=="src/daemon.ts" {print $1}'`, then check `readlink /proc/<pid>/cwd` is this checkout): `pgrep -x node` matches nothing (the process name is `node-MainThread`), and `pgrep -f` / `pkill -f` also match the shell running them and the live `wardd`.
- A second instance reads T3's address from `userdata/server-runtime.json` under its `WARD_T3_HOME` (`{"origin": "http://127.0.0.1:<port>"}`) and its token from `t3-token` in its config folder, so a stand-in server answering `/api/orchestration/shell` tests thread-list behavior without the real T3.
- Annex turns Ward off for the whole server, logging only `T3CODE_WARD_COMMAND=… Ward is off` to `~/.t3/userdata/logs/boot-service.log`, unless `bin/ward`, `bin/ward-prefix` and `bin/ward-bash-env` are all executable; it checks once at startup, so a fix needs a T3 restart. If no agent in a warded worktree has `WARD_ID`, look for that line first.
- `wardd` needs Node 26+ for `node:ffi` (it reads callers' credentials from the control socket); a test instance started as `node src/daemon.ts` prints an ExperimentalWarning for it, which is harmless. From inside a ward, only `port`, `desktop`, `device`, `device stop`, `devices`, `adb-server` and `ls` (own ward) are answered, so drive a test instance from the host.
- Wards need `xdg-dbus-proxy` for their session bus; without it a ward starts with none (no keyring). Run a test instance's ward commands with that checkout's `bin/ward`: an older `bin/ward` joins without the ward's mount namespace and sees the host's files unfiltered.
- Wards have their own PID namespace: a pid printed inside a ward (`$$`, a pid file in `TMPDIR`) is not the host's, so never `kill` it from the host; find the process by its command line, or translate with the `NSpid:` line of `/proc/<host pid>/status`.
- A second instance's devices are real emulators on the host's adb server, as `<WARD_UNIT>-device-<ward id>.service`, with its own base image under its state folder (6 GB, built in 40 s on first use). They take console ports from 5584 down, as the live Ward's do: while both run, each skips ports the other holds. Stop a test instance's with `systemctl --user stop '<name>-device-*'`; never stop `ward-device-*`, `agent-1..3` (emulator-5554 to 5558) or anything on the phone.
- A ward's runtime folder shows only what `ward_runtime_entry` (`libexec/ward-runtime.sh`) lists, from `/run/user/<uid>` and from the instance's `XDG_RUNTIME_DIR`, which a test instance's commands inherit: to check Wayland, sound or pnpm's locks there, run the command with `XDG_RUNTIME_DIR=/run/user/<uid>`, but call the checkout's `bin/ward` without it, or it looks for the live `wardd`, which the ward can't see.
- Inside a test instance's ward, plain `ward` is the installed CLI, which knows nothing newer than `main`: call the checkout's `bin/ward` by its path there too.
- `wardd` and the broker must set `TCP_NODELAY` on anything they relay (`splice` does): without it adb through a ward pulls at 16 MB/s instead of 330, each small acknowledgement waiting 40 ms for a delayed ACK.
- In a ward, Ward's own checkout is read-only, and so is the `.git` its worktrees share: `git commit` fails with "Read-only file system". Commit and push from a clone in `TMPDIR` instead.
